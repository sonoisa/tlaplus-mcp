# 設計の形式検証 (TLA+)

**重要:** このワークフローは、ユーザーの介入なしに、開始から完了まで完全に自動で実行されるように設計されています。各ステップは完了後、ただちに次のステップへ移行してください。思考の途中でユーザーに確認を求めたり、作業を中断したりしないでください。

**引数:** 検証事項 (例: `/verify-design-tlaplus 状態遷移の健全性`)

---

## ステップ1: 準備とコンテキスト設定

1. 現在のタスクコンテキストを確立する:
   - 検証名: `[引数で与えられた検証事項を短いケバブケースに変換]`
   - 日時: `[現在の日時をyyyyMMddHHmm形式で取得]` (日時はISO 8601形式、Bash('date "+%Y%m%d%H%M"')の戻り値)
   - ステアリングディレクトリパス: `.steering/[日時]-verify-[検証名]/`
2. 上記ステアリングディレクトリを作成する。
3. 以下の3つの空ファイルを作成する:
   - `[ステアリングディレクトリパス]/requirements.md`
   - `[ステアリングディレクトリパス]/design.md`
   - `[ステアリングディレクトリパス]/tasklist.md`

## ステップ2: 設計ドキュメントの読み込み

1. `CLAUDE.md` を読み、プロジェクトの全体像を把握する。
2. 以下の設計ドキュメントを読み込む:
   - `docs/*.md` — 設計書
3. 引数で与えられた検証事項に関連する部分を特定し、理解する。

## ステップ3: 検証項目の詳細化 (requirements.md)

1. テンプレートファイル `.claude/skills/tlaplus-verification/templates/requirements.md` を読み込む。
2. 開発者から指定された検証事項を分析し、以下の観点で詳細化・網羅化する:
   - **状態遷移の健全性**: 到達可能性、デッドロック不在、不正遷移排除
   - **並行性の正しさ**: 相互排除、デッドロックフリー、飢餓フリー
   - **時相性質**: 活性、公平性、進行性
   - **振る舞いの整合性**: 設計書間で振る舞い定義が矛盾しないか
3. 各検証項目について以下を定義する:
   - 検証項目名（ケバブケース）
   - アプローチ選択（Pure TLA+ / PlusCal）と選択理由
   - 検証対象
   - 関連する設計要素（具体的なセクション参照）
   - 検証したい性質（形式的に表現可能な性質）
   - TLC config概要（Init/Next/Invariants/Properties）
   - 期待される結果
4. テンプレートのプレースホルダーを具体的な内容に置き換え、`[ステアリングディレクトリパス]/requirements.md` に書き込む。

**このステップが正常に完了したら、決して停止せず、ただちにステップ4に進むこと。**

## ステップ4: TLA+モデル設計 (design.md)

**重要**: `design.md` はサブエージェントが読む唯一の設計仕様書です。サブエージェントは `docs/` 配下の設計ドキュメントを読みません。そのため、`design.md` には TLA+モデル設計に加えて、ステップ2で読み込んだ設計ドキュメントから抽出した設計コンテキスト（関連するエンティティ、状態遷移、並行プロセスなど）を「設計コンテキスト」セクションに凝縮して記載してください。

1. テンプレートファイル `.claude/skills/tlaplus-verification/templates/design.md` を読み込む。
2. **設計コンテキストの抽出**: ステップ2で読み込んだ設計ドキュメントから、検証に必要な設計情報を抽出し、テンプレートの「設計コンテキスト」セクションに記載する:
   - 関連するエンティティ、コンポーネント、プロセスの定義
   - 関連する状態遷移、ライフサイクル
   - 関連する並行プロセス、共有リソース
   - 関連する制約、ルール、不変条件
   - 設計書の該当セクションの要約（出典を明記）
3. `requirements.md` の各検証項目について、TLA+モデルを設計する:
   - **VARIABLE設計**: 状態変数とvarsタプル
   - **TypeOK設計**: 型不変条件
   - **Init設計**: 初期状態
   - **Action設計**: 各アクション（前提条件 + 状態更新 + UNCHANGED）
   - **Next設計**: アクションの選言
   - **Invariant設計**: 安全性不変条件 + 検証コマンド + 期待結果
   - **Temporal Property設計**（該当する場合）: 時相性質 + 検証コマンド + 期待結果
   - **TLC Config設計**: JSON形式のconfig + スコープ根拠
   - PlusCal版V-Nには追加で**Algorithm設計**サブセクション
4. テンプレートのプレースホルダーを具体的な内容に置き換え、`[ステアリングディレクトリパス]/design.md` に書き込む。

**このステップが正常に完了したら、決して停止せず、ただちにステップ5に進むこと。**

## ステップ5: タスクリスト生成 (tasklist.md)

1. テンプレートファイル `.claude/skills/tlaplus-verification/templates/tasklist.md` を読み込む。
2. `requirements.md` の検証項目一覧に基づき、フェーズ1のタスクを具体化する:
   - 検証項目ごとに V-N セクションを作成
   - 各セクションに「.tla 実装」「sany_parse 構文検証」「tlc_check モデル検査」「-results.md 記録」の4サブタスクを配置
3. テンプレートのプレースホルダーを具体的な内容に置き換え、`[ステアリングディレクトリパス]/tasklist.md` に書き込む。

**このステップが正常に完了したら、決して停止せず、ただちにステップ6に進むこと。**

## ステップ6: TLA+モデルの実装・実行 (検証項目ごとのサブエージェント起動)

`tasklist.md` のフェーズ1にある検証項目（V-1, V-2, ...）を一つずつ処理する。**検証項目ごとに個別の `tlaplus-design-verifier` サブエージェントを起動する。**

### 6-0: 検証項目リストの取得

`tasklist.md` を読み込み、フェーズ1の検証項目一覧（V-1, V-2, ...）を把握する。

### 6-1: 検証項目ごとのループ

各検証項目 V-N について、以下を順に実行する。**ループ中に収集した結果はメモリ上に保持し、ステップ7で使用する。**

1. **サブエージェントを起動する:**
   - `subagent_type`: `"tlaplus-design-verifier"`
   - `description`: `"TLA+ verify V-N [検証項目名]"`
   - `prompt`: 以下の情報を含める:
     ```
     以下のステアリングディレクトリの検証項目 V-N（[検証項目名]）について、TLA+モデルを実装・検証し、結果を記録してください。

     ステアリングディレクトリ: [ステアリングディレクトリパス]
     対象検証項目: V-N（[検証項目名]）
     対象ファイル名: [ケバブケース名]

     重要: ステアリングディレクトリ内のファイルのみを読み込んでください。docs/ 配下の設計ドキュメントは読む必要はありません。TLA+コード生成に必要な設計コンテキストは design.md の「設計コンテキスト」セクションに記載されています。

     手順:
     1. [ステアリングディレクトリパス]/requirements.md を読み込み、V-N の検証項目を確認する
     2. [ステアリングディレクトリパス]/design.md を読み込み、V-N の設計セクションと設計コンテキストを確認する
     3. design.md の V-N 設計に基づき、TLA+ コードを実装する
        - ファイルを [ステアリングディレクトリパス]/[ケバブケース名].tla に保存
     4. mcp__tlap__sany_parse で構文検証する（PlusCal使用時は先に mcp__tlap__pluscal_translate を実行）
     5. design.md の V-N「TLC Config設計」から config を構築し、mcp__tlap__tlc_check でモデル検査する（dumpTrace: true を指定）
     6. テンプレート .claude/skills/tlaplus-verification/templates/results.md に従い、
        実行結果を [ステアリングディレクトリパス]/[ケバブケース名]-results.md に保存する
     7. 設計への示唆のみを返す
     ```

2. **サブエージェントの完了を待ち、返却された結果を保持する。**
   - サブエージェントから返却されるのは「設計への示唆」のみ。
   - これを `V-N の結果` としてメモリ上に蓄積する。

3. **必ず `tasklist.md` のフェーズ1タスクを更新する:**
   - ステアリングディレクトリ内に `.tla` ファイルと `-results.md` ファイルが生成されていることを確認する。
   - ファイルが正しく生成されていれば `Edit` ツールで `tasklist.md` の V-N の4サブタスクを `[ ]` → `[x]` に更新する。
   - ファイルが生成されていなければ、タスクに注釈を付ける:
     `[x] ~~タスク名~~ (理由: サブエージェントでエラーが発生。詳細は -results.md を参照)`

4. **次の検証項目 V-(N+1) に進む。全検証項目が完了するまで繰り返す。**

**全検証項目のループが完了したら、決して停止せず、ただちにステップ7に進むこと。**

## ステップ7: 結果分析 (フェーズ2タスクの完全消化)

**このステップは、`tasklist.md` のフェーズ2の全タスクが `[x]` になるまで自動で繰り返されるループ処理です。**
**このステップが正常に完了したら、決して停止せず、ただちにステップ8に進むこと。**

**重要: トークン数節約のため、`-results.md` ファイルを読み込まないこと。** ステップ6でサブエージェントから返却された「検証結論」と「設計への示唆」をそのまま使用する。

`Skill('steering')` を**実装モード**で使用し、以下を実行する。

### フェーズ2タスクの実行（結果分析）

**ループ開始:**

1. `[ステアリングディレクトリパス]/tasklist.md` を読み込む。
2. フェーズ2に未完了タスク (`[ ]`) があるか確認する。
   - **未完了タスクなし**: ループ完了、ただちにステップ8へ進む。
   - **未完了タスクあり**: 先頭の未完了タスクを実行する。

3. タスクの種別に応じて実行する:

   **「全検証項目の結論を確認」タスクの場合:**
   - ステップ6で収集したサブエージェントの返却結果（検証結論）を一覧として整理する。
   - `-results.md` ファイルは読み込まない。

   **「違反が見つかった項目の示唆を整理」タスクの場合:**
   - ステップ6で収集したサブエージェントの返却結果から、不変条件違反・時相性質違反・デッドロック・エラーとなった項目を抽出する。
   - 設計への示唆を整理する。
   - **示唆は `product-requirements.md`、`functional-design.md`、`architecture.md` で用いられる言葉・語彙で記述すること。** TLA+コードのみで説明しないこと。TLA+を知らない設計者でも理解できる表現にする。

   **「検証結果の総合レポートを作成」タスクの場合:**
   - 全検証項目の結果を総合し、設計への示唆をまとめる。
   - **示唆は設計ドキュメントの語彙で記述すること（上記と同じ原則）。**

4. `Edit` ツールで `tasklist.md` の該当タスクを `[x]` に更新する。
5. ループ先頭に戻る。

## ステップ8: 振り返りと報告

1. `Skill('steering')` を**振り返りモード**で実行し、`tasklist.md` の「検証後の振り返り」セクションを更新する:
   - 検証完了日
   - 計画と実績の差分
   - 学んだこと
   - 次回への改善提案

2. 以下の形式でユーザーに最終結果を報告する:

```
# TLA+設計検証 完了報告

## 検証事項
[引数で与えられた検証事項]

## ステアリングディレクトリ
[ステアリングディレクトリパス]

## 検証結果サマリ

| # | 検証項目 | アプローチ | 結果 | 概要 |
|---|---------|-----------|------|------|
| 1 | [項目名] | [Pure TLA+ / PlusCal] | [成立/不変条件違反/時相性質違反/デッドロック/エラー] | [一行説明] |

## 成果物

| ファイル | 説明 |
|---------|------|
| requirements.md | 検証項目一覧 |
| design.md | TLA+モデル設計 |
| tasklist.md | タスクリストと振り返り |
| [名前].tla | TLA+ソースコード |
| [名前]-results.md | 実行結果と解釈 |

## 設計への示唆

[検証結果から導かれる設計改善の提案。product-requirements.md、functional-design.md、architecture.md で用いられる言葉・語彙で記述すること。TLA+コードのみでの説明は禁止。TLA+を知らない設計者でも理解できる表現にする。]

## 次のステップ

[推奨される対応]
```

## 完了条件

このワークフローは、以下の全ての条件を満たした時点で自動的に完了となる。

- ステップ3: `requirements.md` に検証項目が記載されている。
- ステップ4: `design.md` にTLA+モデル設計が記載されている。
- ステップ5: `tasklist.md` にタスクリストが記載されている。
- ステップ6: 全検証項目について `tlaplus-design-verifier` サブエージェントが完了し、`tasklist.md` のフェーズ1の全タスクが完了状態（`[x]`または正当な理由でスキップ）になっている。
- ステップ7: フェーズ2の全タスクが完了状態（`[x]`）になっている。
- ステップ8: `tasklist.md` に振り返りが記載され、ユーザーに結果が報告されている。

この完了条件を満たすまで、自律的に思考し、問題解決を行い、作業を継続すること。

---

### 例外処理ルール

- **設計ドキュメントが存在しない場合**: エラーを報告し、どのドキュメントが不足しているかを明示して停止する。
- **検証事項が曖昧な場合**: 設計ドキュメントの内容から合理的に推測可能な検証項目を自動的に導出し、実行する。
